# Python bindings (foreign/python)

The Python SDK is a PyO3 binding crate that wraps the Rust `laser-sdk` crate. It does not reimplement anything: the wire contract, codecs, and runtime are the Rust ones. Other languages will live beside it under `foreign/` (the same layout Apache Iggy uses).

## Layout

- `foreign/python/Cargo.toml` - the binding crate (`laser_sdk_py` lib, `cdylib`), depends on `laser-sdk` with the managed and agent surfaces and unconditionally enables `iggy/vsr`. Wheels and source builds are VSR-only. Python exposes no protocol switch. The crate is excluded from the root workspace and has its own lock.
- `pyproject.toml` - maturin build, PyPI name `laser-sdk`, import name `laser_sdk` (set via `tool.maturin.module-name`, since the cdylib lib name is `laser_sdk_py` to avoid clashing with the Rust crate's `laser_sdk` lib).
- `src/client.rs` and `src/stream.rs` bind `Laser`, capabilities, the stream/topic accessor grammar, typed topics, publish/batch/replay/ensure, and `producer`/`consumer`/`consumer_group`.
- `src/transport.rs` binds the Laser `Producer`/`Consumer`/`ConsumerMessage` surface over Apache Iggy: direct batch/linger/retry/topology and key/partition writes, first/last/next/offset/timestamp reads, group lifecycle, polling/init retry, typed headers, automatic commits, `commit(message)`, offset inspection/deletion, and async iteration and shutdown.
- `src/publish.rs`, `reader.rs`, `typed.rs`, `schema.rs`, `query.rs`, `watch.rs`, `kv.rs`, `fork.rs`, and `graph.rs` bind the data-platform write and read surfaces. Complex managed shapes cross through serde instead of hand-maintained mirror classes.
- `src/agent.rs`, `agdx.rs`, `agent_runtime.rs`, `workflow.rs`, `runs.rs`, `rbac.rs`, `context.rs`, `memory.rs`, `state_store.rs`, `sign.rs`, and the bridge modules bind provenance, the reliable runtime, coordination, governance, durable state, signing, and edge interoperability. Keep Python behavior and configuration at parity with Rust. Signing rides the same seams as Rust: `laser.agdx(..., signing_key=)` signs every envelope the producer publishes (the Python form of the per-send `.signed_by`), `spawn_agent(signing_key=)` threads the key into `PyAgentCtx` so `respond` and `respond_input` answer correlated commands signed, `verifier=` on connect and on `spawn_agent` enrolls the receive-side registry, and the `agent_ctx` test helper accepts `signing_key=` too.

Read-side coverage is the resumable `Cursor` (`laser.topic(name).replay()`) and `Laser.assemble_context` (conversation replay with a last-N or role filter, plus `token_budget` to trim the selection to an estimated token count). `laser.context(conv).fetch`/`block` take the same `last_n` + `token_budget` pair: Python spells the composed policy as keywords rather than exposing `LastN`/`TokenBudget`/`Chain` objects, and builds `Chain(LastN, TokenBudget)` internally, so context assembly is at parity with Rust and TypeScript. RBAC parity includes `bind_roles(..., expect_revision=...)` and the `authz_history_*` methods. Edge interop is the bridge **adapters**: `Laser.a2a_bridge` (submit/task/cancel/card), `Laser.mcp_bridge` (initialize/list_tools/list_resources/read_resource/call_tool, built with tools/resources/timeout), and the AG-UI methods (`publish_state_snapshot`/`publish_state_delta`/`reconstruct_state`/`agui_events`). A Python agent answers a bridge request with `AgentCtx.respond_input`. The bridges' axum HTTP `router()` is not served from Python (host the endpoint with a Python web framework over the adapter methods). Agent memory and durable state are bound too: `Laser.memory` (writes to the memory topic), `Laser.memory_on_topic(name)` and `Laser.memory_topic(name, partitions=, ttl_secs=)` (configure the topic name, partition count with each scope keyed to one partition, and stream message-expiry, default 30 days), `Memory.vector(embedder)` (standalone in-process semantic memory with no connection), and `Laser.vector_memory(embedder)` (the governed in-process form), all sharing the `Memory.remember` / `recall` / `forget` surface. Embedders can return a vector directly for local work or an awaitable for model service I/O. `remember` writes to the memory topic and the deployment materializes it into the managed key-value read view that `recall` reads by default, so a large topic never folds in process, and each `MemoryItem.source` points back to its origin log record. Folding the topic is the explicit opt-in `recall(folded=True)` / `fetch_folded`, for a small serverless deployment with no read view. The durable handle adds the named-item altitude `set`/`fetch`/`update`/`remove`, each a durable record on the memory topic keyed under the handle's namespace, UnsupportedError on the vector handle, plus the `InMemoryStore` and `FileStore` `StateStore` backends (`get` / `set` / `delete`). The durable relationship layer is the managed `Laser.graph(name)` handle (`upsert` / `neighbors` / `query`), with `node_id`/`edge_id`/`graph_node`/`graph_edge` building the content-addressed string-id dicts and `register_graph` registering a graph projection (exercised by `examples/python/memory.py`, the peer of the Rust `memory` example, whose second half builds and traverses a graph). The conversation lens rides these read surfaces as kwargs and methods (the Rust builder is one method): `graph.neighbors(node, conversation=..)` / `graph.query(conversation=..)`, `query(index).conversation(id)`, and `kv(ns).scan().conversation(id)` / `.delete_many().conversation(id)` each narrow a read to the records one conversation wrote. The borrowing backends are rebuilt per call from the owned `Laser`. The in-process vector backend keeps its items in an `Arc`. MCP tools, resources, and prompts are all supported (the prompt dict deserializes into the SDK's `McpPrompt`, which derives `Deserialize` for this).

- `src/bin/stub_gen.rs` - generates `laser_sdk.pyi` and appends the exception hierarchy (which `create_exception!` does not expose to the stub gatherer).
- `tests/` - pytest: `test_smoke.py` (offline) and `test_integration.py` (the native VSR fork).
- `bdd/python/` - the Python BDD runner over the shared Gherkin in `bdd/scenarios/`. Streaming, capabilities, provenance, and agent run against the native VSR fork. Query and key-value CAS use the transport-free reference engine.

## How the binding works

- **Every async Rust method becomes a Python awaitable** via `pyo3_async_runtimes::tokio::future_into_py`. `Laser` is `Clone` (Arc inside), so each method clones it into the async block.
- **Lifetime-bound builders are not exposed directly.** The Rust builders borrow `&Laser`, so the Python builder classes hold owned, accumulated state and reconstruct + run the Rust builder inside the async block at the terminal (`send`/`fetch`). Fluent setters take `PyRefMut<'_, Self>` and mutate in place.
- **Complex managed inputs/outputs ride serde.** A Python dict deserializes straight into a wire type (`projection`, `binding`, `schema source`, dead-letter capsule) via `pythonize::depythonize`, and structured replies serialize back to dicts. This binds the whole registry/control surface without a class per type.
- **The agent handler** drives a Python `async def handle(ctx, message)` from the Rust reliable consumer: `spawn_agent` captures the running event loop's task locals and runs the consumer inside `scope(locals, ...)`, so `into_future` schedules the coroutine on the caller's loop.
- **Errors** map `LaserError` onto a typed Python exception hierarchy (`errors.rs`), attaching `code` / `retryable` / `unsupported` / ... as instance attributes. `TimeoutError` and `CancelledError` are synthesized with `type(...)` to inherit two bases each (`LaserError` plus `builtins.TimeoutError`, `LaserError` plus `asyncio.CancelledError`), cached in an `OnceLock`, so `except LaserError` still catches them while stdlib `except TimeoutError` / `except asyncio.CancelledError` do too.
- **Readers are async-iterable.** `Cursor`, `WatchReader`, and `TypedRecords` each carry `__aiter__`/`__anext__` (a buffered poll-drain): `async for` yields one record at a time and stops (`StopAsyncIteration`) when caught up, and a fresh `async for` later resumes from the same offsets. `poll()` (batch) and typed `next()` stay. The Laser `Consumer` is different by design: it drives Apache Iggy's live stream and waits for newly appended records until `shutdown()`, with automatic or explicit server-side offset control. Headers preserve Python scalar values and expose exact Apache Iggy kinds through `header_kinds`. Send `(kind, value)`, such as `("uint16", 7)`, when a peer requires an exact numeric width. Rust exposes the same Laser live-consumer behavior, plus Apache Iggy escape hatch.
- **The live consumer avoids an intermediate payload copy.** `PyConsumerMessage` retains Apache Iggy's reference-counted `Bytes` until its `payload` getter creates the one Python-owned `bytes` object required by the language boundary.
- **`Laser` supports `async with`** (`__aenter__`/`__aexit__`): the connection is reference-counted and closes on the last handle drop, and `with_stream`/`with_ops_stream`/`with_control_topic`/`with_dlq_topic`/`with_changes_topic` return aliasing clones over the one connection. `Laser.capabilities()` returns the Rust-negotiated set and `refresh_capabilities()` re-probes the live backend without reconnecting. Python inherits Rust's fail-closed `BackendAnnounce.ready` handling and authoritative per-handle capability overrides rather than reimplementing negotiation.
- **The reliable-consumer knobs are all on `spawn_agent`**: `max_partitions` (per-partition concurrency), `shutdown_grace_ms`, `retry_max_attempts`/`retry_base_delay_ms`, a `dead_letter` callback (`async def on_dead_letter(message, reason, attempts, published)` -> `PyDeadLetterSink`), and a `middleware` list (objects with optional `async before_handle`/`after_handle` -> `PyMiddleware`). `Laser.scatter_report(...)` returns every contracted agent's terminal outcome as dicts. `Provenance` and `AgentMessage` carry `correlation_id` alongside `idempotency_key`.
- **`AgentCtx.fan_out`/`approval_gate` mirror the Rust ctx methods** (`agent_runtime.rs`): `fan_out(skill, payload, *, policy, quorum, deadline_ms, fixed_inbox, principal)` returns `{"ok": [{"agent", "body"}], "failures": [{"agent", "error"}]}`, `approval_gate(reply_topic, prompt, *, timeout_secs)` returns the decision body or raises. Both build a transient `laser_sdk::testing::agent_ctx` internally (borrowed from `PyAgentCtx`'s owned `laser`/`message` fields for the call's duration), since the real `AgentCtx<'a>` is a borrowing type PyO3 classes cannot hold at rest. The module-level `agent_message(payload, provenance)` / `agent_ctx(laser, message, *, agent, respond_on)` functions are the same seam Rust ships as `laser_sdk::testing`: build a message and a ctx with no live consumer, then call a handler function directly in a unit test.
- **The premium and durable seams are bound.** Governance delegates to the Rust combinators. Mandatory quorum voters must affirm, invalid configurations block, and `SwappableGovernor.swap` returns the prior Python policy while `current` reads the active one. Native `Intent`, `Vote`, and `Decision` implement the typed-topic encode/decode hooks, so they publish and replay directly through `Topic.publish` and `Topic.records`. Intent construction, vote casting, and `decide` raise `InvalidError` on invalid state. `Decision.authorizes(intent)` verifies the binding before an effect. Names remain claims unless signing or topic ACLs authenticate authorship. `SwarmActivity` is replay-idempotent and preserves arbitrary verdict names. `CrashContext` exposes `journal`, `dead_letter`, and `last_decision`. Its summary escapes control characters. Keep these behaviors in parity tests and regenerate `laser_sdk.pyi` after changes.
- **Raw parity points remain available.** `Laser.execute_batch` accepts Rust-owned `BatchItem` dicts and returns byte-exact reply frames. `Agdx.status`, `Agdx.fail`, and `AgdxStream.fail` expose the same validated status and structured error terminals as Rust and TypeScript. Every float duration crosses through `Duration::try_from_secs_f64`, so negative, non-finite, or out-of-range values raise `InvalidError` instead of panicking the extension.

## Versioning and naming

- The Python package is `laser-sdk` on PyPI, imported as `laser_sdk`. The internal Rust crate is `laser-sdk-python` (`publish = false`) with cdylib lib `laser_sdk_py`, named to avoid clashing with the `laser_sdk` dependency crate. Maturin renames the built module to `laser_sdk` via `module-name`.
- The Python package version tracks the Rust workspace release train: one version across laser-wire, laser-sdk, and the Python SDK (`0.0.2`), with the dependency pin binding the exact Rust `laser-sdk` it wraps (`=0.0.2`).

## Working on it

- Build into a venv: `maturin develop` (the venv lives at `foreign/python/.venv` in local dev).
- Regenerate stubs after any surface change: `cargo run --bin stub_gen`, then check `laser_sdk.pyi` is current.
- `cargo check` for fast type-checking. The crate is outside the workspace, so the workspace clippy/test gates do not cover it: run them here too.
- Lint and format with ruff (config in the repo-root `ruff.toml`): `ruff check` and `ruff format --check` over `foreign/python`, `bdd/python`, and `examples/python`. The generated `.pyi` is excluded.
- Tests: `pytest -q` against the pinned native VSR server, plus the BDD suite in `bdd/python`. `LASER_TEST_IGGY_SERVER` overrides the R2 artifact for local development.
- Keep the surface in step with the Rust SDK: when a Rust public method or wire type changes, mirror it here and regenerate stubs, the same docs-currency rule the rest of the repo follows.
