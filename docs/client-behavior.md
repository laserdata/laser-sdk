# SDK client behavior

This guide describes how the Rust, Python, and TypeScript clients behave. Operation and envelope versions are 1.

Rust, Python, and TypeScript share the features and defaults listed in [the parity matrix](parity.md). The matrix covers inherent and trait methods, generated builder controls, and standalone SDK functions. Names and construction follow each language.

Managed command errors keep their original result code and message. Rust exposes `LaserError::Command`, Python exposes `CommandError`, and TypeScript exposes `CommandExecutionError`. The shared classifiers preserve unavailable, permission, missing-resource and version-skew results, including unrecognized codes.

## Errors

Every failure has one result code: Rust `LaserError::code()`, Python `code`, TypeScript `code(error)`. The broad classifiers read that code and nothing else, so they never contradict it. Not found is `NotFound`, permission denied is `Forbidden` or `Unauthenticated`, version skew is `VersionSkew`, unsupported is `Unsupported`, stale is `Stale`, and unavailable is `Unavailable`, `TargetUnavailable` or `BackendUnavailable`. A failure is retryable when its code is one of the unavailable codes or `Stale`, or when it is a transient handler failure, a timeout, a deferred policy decision, a routing miss the registry may clear, or a workflow step that timed out. A failed publish, a consumer group setup failure and a typed read whose poll failed classify as the failure under them. The narrow classifiers (version conflict, lease lost, fence violation, not leader, ambiguous mutation, budget exceeded, quarantined, no capable agent, stream or topic not found) name one failure each.

A few codes follow from what the failure means. A missing default stream or respond topic is a configuration mistake (`InvalidArgument`), an invalid identifier is `InvalidArgument`, a cancelled run is `Cancelled`, and a missing KV grant is `Forbidden`. An Apache Iggy `Unauthenticated` reply (code 40) is permission denied and not retryable once it reaches the caller, because the publish path has already re-authenticated and retried. A programming error in a handler (a Rust panic, a TypeScript `TypeError`, `ReferenceError` or `SyntaxError`, a Python `TypeError`, `AttributeError` or `NameError`) dead-letters at once instead of using the retry budget.

The error classes follow one tree in Python and TypeScript: configuration errors (`NoStreamError`, `NoRespondTopicError`, `HandlerConfigError`) under `ConfigError`, the filter fault, oversized record and group setup errors under the filter error, `IdError` under `InvalidError`, `TypedDecodeError` under `CodecError`, and the three routing errors under `RoutingError`. Every filter error carries `reason`: the server's refusal reason, the fault reason of a fault, `oversized_record`, or the group setup cause's reason or `setup_failed`. A fence violation carries `held` and `current` in all three clients. An Apache Iggy transport failure is Rust `LaserError::Transport` and Python and TypeScript `TransportError`, read through `iggy_error_code`.

`wire/fixtures/error_classification_cases.json` pins the code and every classifier for each failure, and the Rust, Python and TypeScript suites run it.

## Agents and sessions

All three clients implement agent sessions. The [AGDX specification](agdx.md#a15-agent-sessions) defines the session records, topics, and reads.

### Sessions

Session writes retain lane identity and reject changed stream or topic generations and partition counts before publication. On managed deployments, a metadata-only Sources check compares the registration using native lane send permission. Aggregate reads keep their existing grants. Explicit registration recovery creates a fresh reference, while old handles remain stale. A refused state snapshot stays pending for retry, and old-generation leases do not heartbeat into a recreated stream.

A session is one conversation with a recorded lifecycle. Its id is the conversation id. `laser.sessions()` returns the session factory. Python takes the configuration as keywords on `laser.sessions(...)`, and TypeScript takes an optional `SessionConfig`.

- `create(label)` derives the session id from the stream, the namespace, and the label, so the same label reaches the same session. `start()` makes a fresh id. Both return a builder that needs `.agent(id)` and ends with `begin()`. `begin()` writes the start record on `agent.sessions` and returns the session and a `SessionLease`. Python also supports `async with builder as session:`. For a labeled session or one with an explicit id, `begin()` first folds the session's lane and control route and refuses an ended session with `LaserError::SessionEnded` (`SessionEndedError` in Python and TypeScript, with `session` and `status`) before writing anything. `resume()` begins the same way and also reopens a session that ended completed or failed: the session index treats its new start record as a resume, and the next terminal ends the session again. A session an agent or an operator canceled stays ended, and `resume()` refuses it too.
- `open(id)` is a lens. It does no I/O, takes no lease, and has no author until `as_agent(id)` names one.
- `end()`, `fail(error)`, and `cancel()` write the terminal record. Every clone of a handle shares one terminal latch. The first verb fixes the terminal state and record id, a repeated call resends that same record, and a different verb fails with an invalid error. `end()` first writes a state snapshot when the session state changed since the last one.
- Rust `Session::run(lease, work)` ends the session by the outcome. A panic is written as a failure with `panic: true` in its detail and then re-raised. Python `async with` and `run` fail the session with the exception type and traceback when the block raises, cancel it when the task is cancelled (`asyncio.CancelledError`), and end it otherwise. The original exception wins when the terminal write also fails. TypeScript `session.run(lease, work)` catches synchronous throws and awaited rejections and records a thrown `Error`'s class name and stack as `exception` and `traceback`. Detached promises stay application-owned, and the SDK installs no process-wide rejection listener. No guard captures a dropped future, process death, or a Rust `panic = "abort"` build. Such a session shows idle once its heartbeat stops.
- A held lease lists the session in the process heartbeat on `agent.heartbeats`. The defaults are a 5-minute idle timeout and a 60-second heartbeat. A zero idle timeout or heartbeat is refused with an invalid error, by the TypeScript setters and by Rust and Python `begin`. Drop or release the lease when the process stops working on the session.
- `sessions().submit(agent, input).from(submitter)` (Python `from_`) writes a submitted session and its first command, addressed to the agent. Chain `label`, `namespace`, `budget`, `tag`, and `operation` as needed. `id()` names the session `send()` will write before anything is sent: the label's derived id, or one fresh id minted for the submission. `send()` returns `Submitted { session, correlation }`. A labeled session that ended completed or failed resumes, and one that was canceled is refused with the session ended error. When the command cannot be published after the submitted status was written, `send()` ends the session failed and returns the publish error, so the session never stays submitted with no work. The agent's reliable consumer marks the session working when it picks the command up and holds a lease while the handler runs. Inside the handler, `ctx.session()` returns the handled record's session, writing as the handling agent, with no lease of its own.
- `sessions().control(stream, id).as_operator(op)` writes `pause`, `resume`, `cancel`, and `force_cancel` records on `agent.control`. The account needs send permission on that topic. `signed_by(key)` (TypeScript `signedBy`) signs each control record, and `Session::signed_by(key)` signs the session's terminal record. The managed index reports a verified signer as `verified_actor` on the event. Untargeted control records carry `agdx.to = *`. `Session::cancel_requested()` is the `cancel_requested` flag of `pending_control()`: a cancel or forced cancel on the session's control route, addressed to the handle's agent or to every agent. It reads the control route whole, so it also answers on open Apache Iggy.
- The reliable consumer follows `agent.control` and records pause and cancel requests for each session it handles, rebuilt from the retained control records on first sight. The follower reads every control partition directly, outside any consumer group, so every instance of a role sees every request. `Session::pending_control()` (TypeScript `pendingControl`) returns them. The runtime never interrupts a handler, so the handler decides when to stop.
- `assemble(policy)`, `model(request, assembled)`, `tool(name, args)`, `record_model_call`, `record_retrieval`, and `record_compaction` record context, model, and tool facts. `assemble(policy)` applies the policy to the session's conversation records only: user and agent commands, responses, errors, tool calls and results, and plain records. Lifecycle, chunks, state, context events, and the model requests the session recorded are left out, so a prompt built from `text()` never contains an earlier prompt. `text()`, the manifest sizes, and the default `TokenBudget` estimate count `ContextMessage::body()` (Python `body`, TypeScript `contextMessageBody`), the envelope body of an AGDX record, not the encoded envelope. A selection over the 1,024-fragment manifest cap is refused with an invalid error before anything is written. `model` and `tool` mark their commands `recorded = true`, so the agent's own runtime never handles them as work. The SDK never calls a model. The application calls its provider and completes or fails the returned call. Tool arguments and JSON model request bodies pass the session's redactor first. The default drops the values of `authorization`, `api_key`, `token`, `password`, `secret`, and `cookie`. `redact(fn)` replaces it. Redaction is a convenience, not a guarantee.
- `state()` returns the session state document. `set`, `patch`, and `replace` append JSON Patch deltas, `snapshot` writes the whole document, and `get` folds the whole retained lane, skipping a state record that does not decode. A handle starts from the folded lane before its first write, so a lens such as `ctx.session()` writes against the current revision. A handle and its clones publish one state write at a time, holding an async lock across the publish, and a write that fails makes the next write start again from the folded lane. The SDK writes a snapshot after every 64 deltas and before `end`. A failed automatic snapshot is logged and retried by the next write. A successful append does not prove a patch applied.
- `context()`, `checkpoint()`, `turns_at`, `turns_since`, `state_at`, and `replay` read the session's records on `agent.sessions` and on the declared topics of a per-agent topic layout, from the partitions those records land on. `context()` keeps the newest records within the context window of each partition, every kind, and `turns_at`, `turns_since`, `state_at`, and `replay` read their checkpoint range whole. The state, budget, lifecycle, and pause participant folds read the whole retained lane, and the control fold reads the control route of `agent.control` whole. A reader takes the layout from its connection, so a process that reads a stream with a per-agent layout declares the same layout in its `SessionConfig`. Each turn carries its display type, such as `session.started` or `tool.call`.
- `Sessions::bootstrap(partitions, retention)` bootstraps the agent topics. When the server announces `sessions` and source registration is on, it also registers the stream as a session source. It waits until the session reads see that registration, retrying temporary read failures until the publish timeout. A refused registration is logged and reported as `registered: false`, never an error, because provisioning can register a stream for an account without session administration rights.
- `Sessions::unregister()` removes the stream's session source registration through the same authenticated managed control path. It needs the same session administration right. The session index for the stream is dropped once the record applies, and a later bootstrap registers the stream again. Control records are never written to the control topic directly. The deployment refuses such a record.

The `sessions` capability is set by the server only when it serves the managed session reads. A client starts with it off and must not infer support from the SDK version. Without it, every write and lane read above works on open Apache Iggy.

### Session reads

- `Sessions::get(id)`, `list()`, `events(id)`, `state(id, history_limit)`, `links(id, surface)`, `sources(id)`, `changes(page, results)`, and `watch(poll_every)` read the managed session index of the factory's stream, and `Session::status()` reads one summary. Python returns the replies as dicts and takes the list and event filters as keywords. TypeScript uses the same names. Without the `sessions` capability they fail with an unsupported error before sending.
- A failed session read is `LaserError::Session` in Rust and `SessionError` in Python and TypeScript, classified by its result code.
- `list()` also filters by `root(id)`, the tree rooted at one session, and `label_prefix(prefix)` (TypeScript `labelPrefix`, Python `root=` and `label_prefix=`).
- `list()` and `events(id)` page by offset: `page(n)` is 1-based and zero reads the first page, and `results(n)` sets the page size, zero for the server default of 10, at most 100 (Python `page=` and `results=`). Every page carries `total_pages`, `total_results` (TypeScript `totalPages`, `totalResults`), its `page`, and the walk's bound, `as_of` and `series` (TypeScript `asOf`). A list holds the sessions newest created first, and a timeline holds the events in server append time order. The first page fixes the bound at the newest change the serving node folded. Every later page passes it back with `as_of(as_of, series)` (TypeScript `asOf(asOf, series)`, Python `as_of=` and `series=`, both or neither), and then holds only the sessions created and the events folded up to that change. So a session that starts or a late record that folds during the walk never repeats or skips a row. A bound from another index, from before a restore, or past what the serving node folded fails as stale, and the walk starts again from the first page. Retention that removes sessions or events during a walk lowers `total_results`, and a reader that sees it fall reads again from the first page with the same bound. A page past the last is empty. Filters match current values, so a session whose status or agents change during a walk can join or leave it.
- A list page reports `rebuilding` while the stream's index on the serving node is rebuilding a reset source partition or catching up after the node started from an empty or restored index. Its `items` and totals can then be incomplete, and an empty page does not mean the stream has no sessions. Rust and TypeScript read a boolean that is false when the reply omits it. The Python dict holds the `rebuilding` key only when it is true, like the `SessionFlags` keys. A detail read for a session the index does not hold yet still fails as not found.
- `SessionInfo.held` counts the records held while the session was paused and not yet handled. `SessionFlags.liveness_unknown` is set while the server's heartbeat tail has not caught up, so `idle` is not meaningful yet. `SessionEvent.verified_actor` names the principal whose key verified a signed record.
- `changes(page, results)` pages the change feed by offset in ascending sequence order (Python `page=` and `results=`). Sequences are dense from 1, so page `p` of size `r` always holds sequences `(p - 1) * r + 1` to `p * r`, and appended changes never shift an earlier page. A page carries `total_results`, the newest sequence, `floor`, the oldest retained sequence or the next one when none is retained, the index's `series`, its `page`, `total_pages`, and `results`, the page size used. Retention prunes the oldest changes without renumbering the rest, so a pruned page reads short or empty and `floor` says where the retained changes start.
- `watch` starts from now in one read of the change feed and never replays retained rows. It follows the feed by sequence, rereading its current page until the page fills and then moving to the next, and reports the changed session ids of each poll. It returns a resync when the series changed because the index was restored or rebuilt, when retention pruned changes it had not read yet, or when a change row lists only part of its sessions. List the sessions again after a resync. A zero poll interval is refused as invalid. The watch iterates asynchronously: Rust `SessionWatch::stream()` is a `futures::Stream` that ends after the first failed read, Python iterates it with `async for`, and TypeScript with `for await`. It follows changes until the caller stops.
- `Laser::read_at(source)` (TypeScript `readAt`) reads the one record a message source reference names with a standard poll. It returns nothing when the record is gone or the topic was recreated, and works on open Apache Iggy.
- [Session sizing](session-sizing.md) reports what a local managed stack measured for role scans, filtered page admission, fold rate, state history growth, and the change feed.

### Pause and resume

- `sessions().control(stream, id).as_operator(op).pause()` writes a pause request that names its participants: the agents given to `participants(..)`, or else the agents the session lane shows working on the session. `resume()` lifts it. On a deployment that indexes sessions, `SessionInfo.awaiting` lists the participants that have not acknowledged the pause in force. An agent that left never acknowledges, so the pause never completes: send `pause()` again with `participants(..)` naming the live agents, and the new request replaces the old set.
- Each named participant acknowledges the request with a `Paused` status that names the request's exact position. An agent outside the set acknowledges when it first receives work for the paused session.
- An agent holds work that arrives while the session is paused. It writes a `session_parked` record on the lane before it commits the source, and never treats parked work as handled. After the resume it acknowledges with a `Working` status, handles each held record at least once before new work, and writes `session_unparked` after each one. A crash between the effect and that record can repeat the effect, so effects still need an idempotency key or a fenced write.
- A cancel while paused ends the session as canceled. Held records are not handled. `Session::parked()` lists them with a `complete` flag that is false when the bounded read did not reach the oldest retained record of the session's partition or a held record can no longer be read back. Retention that removed older records of the partition does not make it false. The managed index counts them as `SessionInfo.held`.
- The handler is never interrupted. Recovery after a restart, rebalance, or reconnect rebuilds the held set from the lane and reports incomplete recovery instead of dropping work.
- Timelines show the holds as `session.parked` and `session.unparked`. No capability advertises the pause runtime yet.
- A session's control route is the `agent.control` partition its conversation id hashes to (XXH32 with seed zero, modulo the partition count), the partition every SDK writes its control requests to. The SDK control book, the log fold and the managed backend apply only requests on that partition, whatever order partitions are read in. A request on any other partition is never applied, and `PendingControl.control_conflict` (TypeScript `controlConflict`) and `SessionInfo.flags.control_conflict` report it. A recreated `agent.control` (a new topic generation) starts every session's control history again: the follower notices the new topic within 5 seconds and reloads, and the backend drops the old requests when the first record of the new generation folds. Changing the partition count of an existing `agent.control` is not supported, recreate it instead.
- An agent that starts before `agent.control` exists keeps looking for it with a backoff that grows to 30 seconds. Once the topic appears, the agent follows it, rebuilds its pause state from the log, and starts the pause runtime, so pause holds work from then on in Rust, Python and TypeScript alike.

### Session budgets

`Session::over_budget()` reports whether a session passed the budget in its start record: the summed input and output tokens of its records over `Budget.tokens`, or their summed `cost_micros` over `Budget.cost_micros`. The start record that opened the session applies, the first one or the one that resumed it. With the `sessions` capability it reads `SessionInfo.over_budget` from the index. On open Apache Iggy, for a session the index does not know yet, and while the index is unavailable or catching up, it folds the whole retained lane by the same rule. A lane whose start record retention removed reads as within budget and logs a warning. A workflow checks its run session after the cancel check at every step boundary, compensates the completed steps, and returns a budget exceeded error, and every budget breach of a workflow ends the run session failed with reason `budget`. The reliable consumer checks a session before handing its work to the handler, once per session per poll batch, and only on a deployment that serves sessions, because folding the lane for every record would cost too much on open Apache Iggy. Work for a session over its budget ends the session failed with reason `budget` and an error naming the ceiling, and is committed without reaching the handler. The terminal latch keeps that failure to one record, and later work for the session is committed the same way. Budget reads are eventually consistent, so a budget is a cooperative limit, not a hard spending cap.

### Stream-scoped resource names

- A `Laser` with a default stream scopes every managed resource name it sends to that stream as `stream:<stream>/<name>`: key-value and memory namespaces, lease and fence namespaces, the key registry, graph names, projection IDs and index names, query indexes, fork IDs, and the change-feed index filter. A name already scoped to that stream is sent as is, and a `stream:` name for another stream is scoped like a local name, so caller input never reaches another stream. Re-scope with `with_default_stream` or use bare naming to address another stream. A default stream containing `/` cannot be scoped, so its managed calls are refused as invalid. A `Laser` without a default stream sends bare names.
- `Laser::resource_name(name)` (TypeScript `resourceName`) returns the name a handle sends. `Kv::resource_namespace()` and `ForkHandle::resource_id()` (TypeScript `resourceNamespace` and `resourceId`) return a handle's scoped name.
- Listings of namespaces, projections, and forks return only the handle's own scoped names, with the prefix stripped.
- The projection selector header `agdx.ref` on a published record keeps the local projection ID. The managed backend resolves it against the bindings of the record's own stream and topic, first as written and then as `stream:<stream>/<ref>` with the stream the record was read from, so a scoped projection matches a bare header and a record can never select another stream's projection.
- Consumer filter catalog names are not scoped by the client. A group's own filter carries the name the caller configured as a label and is found by its owner, the group's verified identity, which includes the stream ID and the stream creation time, so two streams cannot share one. A raw catalog `Register` request sent through the low-level `mutate` call carries its name as written: the streaming server authorizes a scoped name against the named stream, and a deployment in stream tenancy mode refuses a bare one.
- Schema requests carry the default stream, so a writer schema ID resolves in that stream's registry. Each stream has its own registry, numbered from 1, so two streams can hold the same ID, and a client without a default stream or with bare naming uses the deployment-wide registry. The managed backend decodes a record under its stream's registry first, then the deployment-wide one, and in stream tenancy under the stream's registry only. `ConsumerFilter::with_schema_stream(stream)` names the registry a filter's `schema_refs` resolve in.
- Python `Laser.query(index)`, `Laser.query_target` with an operational index, and `QueryRequest.fork(id)` scope their names like Rust and TypeScript. Python `Kv.namespace` and `ForkHandle.id` return the caller's local name, also when the caller passed a scoped one.
- `ResourceNaming::Bare` opts out and sends every name exactly as written: Rust `LaserBuilder::resource_naming(ResourceNaming::Bare)` or `laser.with_resource_naming(ResourceNaming::Bare)`, Python `Laser.connect(..., resource_naming="bare")` or `with_resource_naming("bare")`, and TypeScript `resourceNaming("bare")` on the builder or `withResourceNaming("bare")`.
- `Capabilities.stream_tenancy` (TypeScript `streamTenancy`) is set when the deployment scopes every managed name to one stream. On such a deployment a scoped `watch` reads its stream's own change topic, and a role grant that spans streams fails with `AuthzError::TenancyViolation`.

### Wire

- Codes 1_000_700 to 1_000_703 and feature bit `1 << 4` are reserved and never reused.
- The display types include `invalid` for a record whose header and body name different identities, and `session.parked` and `session.unparked`.
- `ChangeRecord.stream` names the stream a change record belongs to when the deployment publishes per stream.
- The HTTP path helpers percent-encode every name they place in a path: fork IDs, KV namespaces and keys, graph names, graph nodes, graph IDs, and projection IDs. A scoped name is one path segment. Pass names unencoded, or they are encoded twice.
- `Capabilities::from_versions` sets `sessions` from the `SESSIONS` feature bit, so `GET /agdx/capabilities` reports session reads when the deployment serves them.

### Topics and bootstrap

- `AgentTopic` has `Sessions`, `Streams`, `Heartbeats`, `Control`, `Memory`, `Audit`, `Registry`, `WorkflowJournal`, `Dlq`, and `Custom`. Every agent record rides `agent.sessions` unless the caller names another topic.
- `Laser::bootstrap(partitions, retention)` requires a `TopicRetention` for `agent.sessions`. `TopicRetention::expire_after(age)` is the usual choice. A policy that never expires and has no size bound is refused. Bootstrap also creates `agent.heartbeats` with a one-hour expiry and `agent.streams`, `agent.memory`, `agent.dlq`, `agent.audit`, and `agent.workflow_journal`. The first agent card creates `agent.registry`. Bootstrap never creates `agent.control`, which provisioning creates with an operator-only send grant. A stream that already exists is used as it is.
- The default memory topic is `agent.memory`.
- `ContextAssembler` and `ContextScope` read `agent.sessions` by default.
- Bootstrap, agent, session and memory topics take the server's default replication factor. Only `Topic::ensure` and the producer's topic creation take a factor of their own (see Publication and reads).

### Dispatch and replies

- The reliable consumer classifies every record before dispatch as work, observational, reply, lifecycle, control, or foreign. Only work for the handler's operations reaches the handler. Everything else is skipped and committed, and `Laser::consumed` reports it as `Skipped`. The author never decides the class, so an agent can send work to itself. A model or tool call a session records carries `recorded: true` and is observational, so it never reaches the session's own agent as work. An `input_request` prompt reaches only a handler that lists `input_request` among its operations. Rust `Agent::builder().operations(..)`, Python `spawn_agent(operations=)`, and TypeScript `AgentBuilder.operations(..)` limit the command operations a handler serves.
- A panic in a Rust handler becomes a non-retryable error. The record dead-letters as rejected and the consumer keeps running.
- A retryable `before_handle` middleware error is retried under the handler's retry policy and dead-letters as retry exhausted once the attempts run out. A non-retryable one dead-letters as rejected without running the handler.
- A dead-letter publish that fails with a retryable error is retried in place on the consumer backoff, up to the consumer failure budget. A publish that keeps failing stops the consumer with the record uncommitted, so it is read again once the consumer runs again, and the dead-letter sink sees each final outcome.
- A dead-lettered correlated command is answered on `respond_on`: an AGDX error to its source, addressed to it, caused by it, signed with the agent key, and carrying the dead-letter reason code under `dead_letter_reason`. A contract reads the refusal at once instead of waiting out its deadline, and reports `NotConsumed` only when that answer says the command expired before pickup.
- `ack_on_pickup` requires `respond_on`. Rust `Agent::spawn` and `ReliableConsumer::run` fail with `LaserError::Config`, Python `spawn_agent` raises `ConfigError`, and TypeScript `AgentBuilder.build()` and `new ReliableConsumer` throw `ConfigError`. The pickup status is addressed to the command's source.
- Under `SerialPerPartition`, a record of a new partition at the lane cap closes the lanes holding no record, or waits for one to drain while the other lanes' completions commit, so no record runs on the polling task.
- Delivery runs on the consumer-group consumer with explicit commits. Each agent id has its own group, named after the agent id unless the builder names another. An agent id can be 256 bytes and a group name at most 255, so an agent whose id is 256 bytes names its group explicitly, and spawning it without one fails. On `agent.sessions` and `agent.control`, when the server resolves group policies and serves filtered reads and the filter catalog, and the `Laser` was built from a connection string, the runtime binds the agent's group to the addressee filter `agdx.to In [<agent>, "*"]`, saved under the name `agent-addressee` (`ADDRESSEE_FILTER_NAME`), before it reads, and refuses a group bound to another filter. Otherwise, on open Apache Iggy or with a client the application brought, the group stays unbound and the client classifies every record.
- A record that `send_agent`, `request`, or their Python and TypeScript forms (`send_agent`/`sendAgent`, `request`) publish on `agent.sessions` or `agent.control` without a target carries `agdx.to = *`, the same rule the envelope path applies, so an agent whose group is bound to the addressee filter still receives it. A named target rides unchanged, and other topics keep the caller's headers verbatim.
- A record on a shared session topic that carries no `agdx.to` at all, such as a raw `topic("agent.sessions").send(...)`, never passes the addressee filter of an agent whose group is bound to it. A server with group-aware reads keeps the record on the log, and that agent neither handles nor dead-letters it. Open Apache Iggy classifies on the client and dead-letters the malformed record.
- A dead letter keeps the record's conversation, also for a record that did not decode. A dead letter never fails its session unless the agent runs with `fail_on_dead_letter`: Rust `Agent::builder().sessions(SessionConfig::new().fail_on_dead_letter(true))`, Python `spawn_agent(..., sessions=laser.sessions(fail_on_dead_letter=True))`, and TypeScript `AgentBuilder.sessions(new SessionConfig().failOnDeadLetter(true))`. That configuration also shapes the `ctx.session()` handles.
- A request waiter accepts a reply only when it carries the request's correlation, belongs to the request's session, is a response or error when it has an envelope, and is addressed to the requester when the request named one. The request's own record never answers it, even on the same topic.
- `respond`, `reply_on`, and `respond_input` address the requester and carry the request's record id and full log position as the cause. A generic reply always carries a correlation, the request's own or its message id. Python runs the Rust context paths, so its replies carry the same correlation, ancestry, addressee, and cause.
- An input request (`request_input`, `request_input_from`, `approval_gate`) publishes an `input-required` task status, then the prompt as an `input_request` command, which reaches only an agent listing `input_request` among its operations. A request that names its approver accepts only a reply that approver authored, signed by it when a verifier is configured. `approval_gate(approver, reply_topic, prompt, timeout)` (TypeScript `approvalGate(approver, replyTopic, prompt, timeoutMs)`) returns an `ApprovalGrant`, and an AGDX send that carries it (Rust `AgdxSend::with_grant`, Python `grant=`, TypeScript `withGrant`) proceeds through a governor step-up in the grant's conversation, recorded as a step-up decision that was effected. Run by a reliable consumer that reads `reply_topic` on a stream with `agent.control` (the pause runtime), the gate parks instead of waiting: its first pass publishes the prompt and returns `PolicyDeferred`, the runtime parks the record and the session's later work and frees the consumer for other sessions, and the decision replays the record through the handler, where the gate returns the grant, the rejection, or `Timeout` once the deadline passed. Handler code before the gate runs again on that replay, so it must be idempotent. Without the pause runtime, or with another reply topic, the gate waits in place.

### Partition routing

- A stream's layout is `SessionLayout::Shared` (the default), `PerAgentTopic(map)`, `PerAgentPartition(map)`, or `SinglePartition`. Python spells them `SessionLayout.Shared()` and the others, and TypeScript uses `{ kind: "shared" }` and the other kinds. Declare a layout through the session configuration. It then holds for every later send on that stream through the same connection.
- Lifecycle and state always ride the session's partition on `agent.sessions`. In the per-agent partition layout, a command, response, error, or chunk addressed to a declared agent lands on that agent's partition. A command is keyed by its addressee and a reply by its requester. Every other record rides the session partition. Partition ids are zero-based, and the mapping must be declared because hashing agent names can collide.
- In the per-agent topic layout, the map names each declared agent's own topic. On `agent.sessions` sends, a command addressed to a declared agent goes to that agent's topic, and a response, error, or chunk goes to its addressee's declared topic, keyed by session. Plain records sent with a target follow the same rule. Lifecycle, state, broadcast records, and records for an undeclared agent stay on the session lane. `Sessions::bootstrap` creates the declared topics with the lane's partition count and retention and refuses a declared `agent.sessions` or `agent.control`. A reliable consumer for a declared agent that listens on `agent.sessions` reads its own topic plus `agent.control`. A request, contract, input request, or MCP tool call by a declared requester awaits its reply on the requester's topic. Session reads cover the declared topics because bootstrap registers every topic of the stream. Python spells it `SessionLayout.PerAgentTopic(topics={"planner": "planner.inbox"})`, TypeScript `{ kind: "perAgentTopic", topics: new Map([["planner", "planner.inbox"]]) }`.
- `SinglePartition` bootstraps every agent topic with one partition.
- Every record on `agent.sessions` carries `agdx.to`, with `*` when it is addressed to every agent.

### Context, memory, and lineage

- `ContextMessage` carries `timestamp_micros`, the server append time, and the numeric `stream_id` and `topic_id` beside the topic name, so a reader can build a source reference without a lookup.
- `ContextPolicy` has `name()`, `version()`, and `selection(history)`, which returns the kept and dropped records and the reason. A context manifest records the policy name and version.
- Every SDK uses one token estimate: the byte count divided by four, rounded up.
- `ScopedMemory::with_lineage(origin, producer)` stamps remembered items with the record that motivated them and the agent or policy that wrote them. `Session::linked_memory()` does this for the session's current record.
- `Kv::in_session(reference)` and `GraphHandle::in_session`, `produced_by`, and `sourced_from` link key-value and graph writes to a session. `Session::kv(namespace)` and `Session::linked_graph(name)` return handles that are already linked.

### Workflows and child sessions

- `Workflow::run` is a root session whose id is the run id. Each step and compensation is a child session with an id derived from the run, the step label, and the attempt. The engine checks `agent.control` for a cancel request at every step boundary, compensates, and returns a cancelled error. It then checks whether the run session is over its budget, as [Session budgets](#session-budgets) describes. A check that fails to read compensates before its error returns.
- A workflow refuses its configuration before it writes anything: a duplicate step label, a broadcast step, an exclusive all-capable step, reassignment without exclusivity, an exclusive step on a deployment without fenced leases, an unknown dependency, or a cycle is an invalid or unsupported error.
- A step that does not complete fails the run with `LaserError::StepFailed { run, step, reason }` (Python and TypeScript `StepFailedError` with `run`, `step`, and `reason`). The reason is `timed_out`, `failed` (the target replied with an error), `not_consumed` (the target's consumer dropped the command past its deadline), `unverified` (the verifier rejected the reply), or `no_completion` (no capable agent completed an all-capable step). Only `timed_out` is retryable and its code is `DeadlineExceeded`. An exclusive step whose lease is lost fails with the lease-lost error.
- Every step has a completion deadline, 30 seconds unless `StepHandle::deadline` (Python `deadline_ms=`, TypeScript `deadline(ms)`) sets another, never past what the wall-clock budget has left. It bounds the step's build, its dispatch, its verification, and its completion record. A build or verification that runs past it fails the step as `timed_out`.
- The journal on `agent.workflow_journal` records the run's start, each dispatch with the reply topic's positions at send time, each completion with the agents that ran it, and each compensation that completed. A run under an explicit `run_id` replays the whole retained journal of the run, never a window, and reopens its run session through `SessionBuilder::resume`, so a run that ended completed or failed runs again under the same id while a canceled run is refused with the session ended error. A step recorded complete never runs again. A step dispatched without an outcome is answered by a reply that landed after its recorded positions, and otherwise sent again with the same correlation and an idempotency key derived from the run, the label, and the attempt, so the target's duplicate suppression drops a command it already handled. A compensated step counts as undone and runs again under a new attempt. A journal that holds the run's records without its start, or holds none while retention has removed the head of a journal partition, fails with `LaserError::JournalTruncated` (Python and TypeScript `JournalTruncatedError`, code `ExpiredSnapshot`) instead of running the steps again. An all-capable step in flight when the run stopped is scattered again.
- Compensation runs in reverse completion order for every step with an effect, a verifier-rejected step included, and goes to the agents that ran the step under the principal the step's route required, never a fresh resolution. An all-capable step compensates every agent that completed it. A compensation that does not complete is reported (a `tracing` warning in Rust and Python, a `LaserWarning` process warning in TypeScript) and the rollback goes on.
- An exclusive step holds a fenced lease with a 15-second lifetime, renewed at half of it and never past the step deadline. A live lease of an earlier holder, a run that stopped while holding it, is waited out inside the step deadline, so resuming a crashed run does not roll the saga back. On a timeout with `OnTimeout::Reassign`, a capability route sends the next attempt to a capable agent other than the ones that timed out, and to one of those again only when no other agent is capable. A route that names one agent sends every attempt to it. Dropping the Rust run future or cancelling the Python task stops the run at once without compensating and releases a held lease. Aborting the TypeScript `signal` cancels the run at the next step boundary and compensates.
- `ContractBuilder::parent(parent, root)` runs a contract as a child session. It writes the child's submitted start before the command and ends the child by the outcome, failed when the command did not publish.
- Every contract command carries `deadline_micros`, the earlier of the consumption expiry and the completion deadline, so a target that picks it up after its caller gave up drops it and answers the drop. Scatter branches, fan-out branches, workflow steps, and compensations carry their deadline the same way. A contract awaits its acknowledgment and terminal on the shared reply dispatcher, and only a record in the command's session addressed to the contract's source answers it.
- `Laser::scatter` and `scatter_report` (Python `gather=`, TypeScript a `GatherPolicy` argument) and `AgentCtx::fan_out` gather under `GatherPolicy::{RequireAll, Quorum(n), BestEffort}`. A quorum below one is refused in all three clients. `ScatterReport` and `Gather` name the branches the policy cancelled and whether the gather met its policy: every branch under `RequireAll`, at least `n` under `Quorum(n)`, at least one under `BestEffort`.
- `A2aBridge::submit_in(parent, root, params)` and `McpBridge::call_tool_in(parent, root, name, params)` run a bridge call as a child session. Python takes `root=` as a keyword, and TypeScript names them `submitIn` and `callToolIn`. MCP ends the child by the tool result. A2A leaves that to the handling agent.
- A bridge call and an input request are addressed to every agent (`agdx.to = *`) unless the caller names one, so on a shared `agent.sessions` topic every listening agent receives them. `A2aBridge::submit_to` and `submit_in_to`, `McpBridge::call_tool_to` and `call_tool_in_to`, and `Agdx::request_input_from` take a target agent and address the command to it alone. Python takes `target=` on `submit`, `submit_in`, `call_tool`, `call_tool_in`, and `request_input`. TypeScript takes a `{ target }` option on `submit`, `submitIn`, `callTool`, `callToolIn`, and `requestInput`. A bridge's `with_target(agent)` (Python constructor `target=`, TypeScript `withTarget`) addresses every bridge call that names no target, the JSON-RPC routes included.
- With a signing key (`with_signing_key`, Python `signing_key=`, TypeScript `withSigningKey`) both bridges sign every command they publish, so an agent with a verifier accepts them. Under a verifier the answer to an addressed bridge call must be signed by its target, so another enrolled key cannot answer for it.

### Other behavior

`Laser::spawn_subconversation(parent, author)`, Python `Laser.spawn_subconversation(parent, author)`, and TypeScript `Laser.spawnSubconversation(parent, author)` require the spawning agent's identity. A handler context supplies its own agent identity when it creates a child conversation, so the child's author is the spawning agent and never the incoming sender.

Log memory searches use the supplied text to filter items before applying the result limit. Keyword, semantic, and hybrid searches use lexical matching on log memory. Recent recall ignores query text and orders by recency only. This applies to the managed memory view and the folded log view in all three clients.

A forget or feedback call with a conversation in its scope acts only on an item remembered in that conversation. `ScopedMemory.forget` and `improve` always pass their conversation, so they never remove or reweight another conversation's item. A call without a conversation acts on the item in any conversation. The log fold, the in-process vector index, and the managed memory view apply the same rule in all three clients.

A forget is a tombstone that carries the server append time of its record. The log fold and the managed memory view drop every write of the item at or before that time, whichever partition it rides and in whatever order the partitions are folded, and keep a write made after it, so remembering a deduplicated fact again after a forget brings it back. A forget never removes a write newer than itself. Feedback sums into a weight per item, counted even when it is folded before its item. Every strategy except recent ranks by that weight first and then by arrival, and a weighted item reports the weight as its `score` with an `Auto` signal. The managed memory view row carries the weight as `weight`.

A deduplicated id hashes the stream, agent, user, application, and conversation of the scope with the kind and the body, so the same fact remembered in two conversations is two items. A log memory handle writes to one stream: a remember, forget, or feedback call whose scope names another stream fails with an invalid-argument error before anything is sent, and recall with another stream returns nothing. The in-process vector index keeps the stream as a tag it filters by. A folded recall (`recall_folded`, `folded()`, `folded=True`) reads every partition until it is drained, however far behind the handle is, so it reflects the whole retained history.

Managed memory recall orders items by the server append time of their source record, then by source position. Consolidation keeps the newest items by the same arrival order in all three clients. The memory view row carries the server time as `timestamp_micros`. Periodic agent consolidation passes the agent's own scope, with the agent id set and every other field empty. A consolidator with a summarizer writes one durable `Summary` per conversation, scoped and attributed to that conversation. The summary id is the deduplicated id of the summary scope, the `Summary` kind, and the ids of the turns it covers as 16 big-endian bytes each in ascending order, so a pass over turns that already have their summary calls no summarizer and writes nothing.

`Laser::consumed` (Python `consumed`, TypeScript `consumed`) returns `Skipped` when an agent's consumer group has committed past a record that is not work for that agent, such as a record addressed to another agent, a reply, or a status record. The status names the classification, for example `foreign`. Records that the group handled report `Consumed`. A probe of a named consumer, or of a record that is gone or does not decode, keeps the offset-only answer.

All three clients stamp record headers through one shared encoder. Generic records carry the fence, deadline, and token counts as typed `u64` headers and the cost as a typed `f64`. Envelope records also carry their author as `gen_ai.agent.id`. An `agdx.to` value of `*` addresses every agent and decodes as no single target.

Every node answers every managed request, so a client spreads its managed requests over the nodes and needs no particular node for correctness. Each client keeps one node of its own: it reads the cluster's replica ids once and picks one by a random key minted for that `Laser` handle, which clones share. A failed link moves the client to the next node, and the request goes there, at most once per node. A replica id the cluster no longer names reads the roster again once. The three managed authorization writes (define role, delete role, bind roles) go to the metadata primary. A filtered read and a preview go to the source partition's primary when the route lookup answers, and to the client's own node otherwise, which refuses with `NotPrimary` when it does not store the partition. The route is looked up again after `NotPrimary`, an unknown replica, a lost link, a recreated partition or a lost assignment. A request waits up to the SDK's operation deadline for a node that is reconnecting before it moves on. A managed mutation is the exception: its roster reads, reconnects, attempts and backoff share one 30-second deadline, and each attempt is bounded from one second up, doubling, so a stopped node costs about a second before the same frame goes to the next node. A `BackendUnavailable` refusal moves the request to the next node whether or not it carries the answering node's positions, and `Pending` repeats on the same node. Once an attempt's outcome is unknown, a later `Forbidden`, `Unauthenticated` or `StepUpRequired` refusal, or a refused link, ends the call with an ambiguous mutation error that names the operation identity, never with the refusal alone, because the earlier attempt may still apply. A filtered read or acknowledgment is the exception: a backup's `unavailable` refusal looks the route up again and resends once, and a request to the known primary that has not answered after a second looks the route up again every second and moves to the node the cluster names, so a stopped primary costs about a second instead of the operation deadline. An acknowledgment that still finds no primary is sent again with the same target on the managed mutation backoff for up to 30 seconds, so it never stores past what was delivered. Rust, Python and TypeScript behave the same. Python goes through the Rust client.

Rust keeps an agent running only while its `AgentHandle` lives. Dropping the handle signals a graceful worker shutdown and stops periodic consolidation. Call `shutdown().await` to see drain failures. After a failed `ready()`, which already returned the error, `shutdown()` returns `HandlerConfig` instead of panicking.

A spawned agent with capabilities publishes its card with its inbox (the topic it was spawned on) and a ttl of three session heartbeats, republishes it every heartbeat, and on a graceful stop republishes it with every skill unavailable and clears its presence, in all three clients. `AgentScope::advertise` publishes a card with the inbox and no ttl. The default `InboxRoute::Advertised` resolves an agent's live presence inbox and falls back to its card inbox, and on Apache Iggy, which keeps no connection metadata, it reads no presence at all, so contracts, scatter, fan-out, and workflows route there without a fixed inbox. A capability route picks only among agents that have an inbox under its inbox route. A named route (`Router::To`, `ToPrincipal`) to an agent an operator quarantined fails with `LaserError::Quarantined` (Python and TypeScript `QuarantinedError`).

Python `Laser.close()` does not print the Iggy producer's `Client has been shutdown` warning. That one record, which every cached producer writes when its own client closes, reaches Python logging at debug. Every other Rust log record keeps its level.

AG-UI rendering reads every retained record of the conversation on the topic in all three clients and emits `RUN_ERROR` for failed or rejected task status. It uses the status detail when available. Completed and canceled task status emits `RUN_FINISHED`. Every event sits inside a run: an event outside one opens a run, a run closes its open messages and tool calls before it finishes, and the rendering ends with no run open. `TOOL_CALL_RESULT` carries `messageId`.

Fold snapshots name the stream, its creation time, the fold, and each topic generation. Built-in snapshot stores require a fold name. Managed snapshots use the stream, conversation, and fold in their key. State replay checks source generations and resumes each topic at its own saved offsets. `ConversationState` replay folds the whole requested range for a full, offset, checkpoint, or position bound. A `Last(n)` bound stays windowed.

A query above `MAX_PAGE_SIZE` fails with an invalid-argument error before any round trip.

## Publication and reads

A publish that gives up reports the confirmed ranges and the unconfirmed records. Retries keep the message IDs of the first attempt. See [publish recovery](publish-recovery.md).

A batching producer keeps its timer running after a failed timer flush. The next `send`, `flush`, or `close` reports the kept failure. A `send` that finds it refuses its own record and adds it to the unconfirmed records. `flush` and `close` drain the queue first. Inspect the confirmed ranges before you retry.

Topic creation settings apply only when the topic is absent. Two clients that create the same topic at once both succeed. A background send returns once the queue accepts the records. `flush` writes everything queued and `shutdown` drains the queue and stops the producer, from any clone, and both report the background failures no error callback took. A TypeScript background error callback can return a promise, and a failing callback does not replace the original publish failure.

Live waits end with a typed timeout. TypeScript keeps an unfinished poll so the next call can still receive its late record. Cancelling a wait does not acknowledge a record that was never delivered.

A query with a zero row ceiling sends nothing. Results and pages stay bound to the execution ID that was requested.

A query result's fields come from the query and the fields the index's projections declare, never from the rows of a page, so every page of one query carries the same schema. A field declared `int`, `float`, `bool` or `text` arrives as a long, double, boolean or string, and a stored value that does not fit its declared type is null. A field declared without a type, a selected field no projection declares, and every raw SQL column are `variant`: each value keeps its own tag, as the backend stored it. `select_fields` (TypeScript `selectFields`) returns exactly the selected fields in the order given, then the provenance fields, and a query without text or vector search reads only those fields from the backend. Walks return rows bound to their fields: `QueryRow` in all three clients, with `value`, `value_text`, `value_i64`, `value_u64` and `field_index` (TypeScript `valueText`, `valueI64`, `valueU64`, `fieldIndex`), and Python also reads `row["name"]`, `row[0]` and `keys()`. `fetch_all` (TypeScript `fetchAll`) returns a `QueryRowSet` with the rows and `frontier_moved` (TypeScript `frontierMoved`), and the bounded `rows` and `rows_typed` walks report `frontier_moved` too. Each page carries the frontier the store had applied before it read the page. A later page served at another frontier than the first may repeat or miss rows written in between, so `frontier_moved` turns true, and the walk still finishes.

TypeScript filter, `whereEq` and raw SQL parameter values take a tagged value or a native `string`, `number`, `bigint`, `boolean`, `null` or `Uint8Array`, inferred like Python: a safe integer or a bigint in the signed 64-bit range is a long, another finite number a double. A non-finite number or an out-of-range bigint fails with an invalid-argument error. Rust infers from the Rust type, so `90` is an `i32` int and `90_i64` a long.

A raw SQL statement that reads an index no binding names answers `IndexNotFound`, and one that reads an index bound to a backend the deployment has not configured answers `Backend`, as a structured query of that index does.

A query deadline is at most 25 seconds away. A later one fails with an invalid-argument error before any round trip. The relative deadline (Rust `deadline`, Python `deadline`, TypeScript `deadline`) is counted from the start of each call and of each page of a walk, and every call and every page carries a fresh execution identity, so a request kept and fetched again later gets a full budget. An absolute deadline (`deadline_at_micros`, TypeScript `deadlineAtMicros`) bounds every later call and page. A terminal that implies a payload or a one-row limit, such as `fetch_one` or `fetch_typed`, applies it to that call only and leaves the request as it was. The server stops waiting for the backend at the deadline and replies `DeadlineExceeded`. The client waits 2 seconds past the deadline for that reply and then fails with a timeout. A timeout does not prove the query stopped. The backend's own statement timeout ends a statement that is still running.

TypeScript MessagePack writes named maps and the shortest integer encoding. It rejects integers outside the signed and unsigned 64-bit ranges. Bodies the caller has already encoded stay opaque bytes.

A topic can be created with a replication factor, the number of nodes that store each partition: Rust `Topic::ensure(partitions, Some(factor))` and `ProducerBuilder::replication_factor(factor)`, Python `ensure(partitions, replication_factor=)` and `producer(replication_factor=)`, TypeScript `replicationFactor`. Without one the server's `[cluster] default_replication_factor` applies, which is every node unless an operator set a number. A factor must be 1 to 32 (`MAX_REPLICATION_FACTOR`), checked before anything is sent with an invalid-argument error (`replication factor must be 1..=32`). The server also refuses a factor above the cluster's node count, which surfaces as the Iggy error (`InvalidReplicationFactor` or `InvalidOptionValue`). An existing topic keeps its factor. The upstream producer cannot pass a factor, so a producer with one creates the topic itself before it starts. No SDK call returns topic details, the raw Iggy client's `get_topic` reports each partition's `members` and `in_sync_members`.

On a cluster wider than a topic's factor a node stores only some partitions. Every partition read, filtered read, acknowledgment, filtered wait, held read of the reply reader and the control follower, native consumer read and publish goes to the partition's primary, which is always a member. A filtered read, acknowledgment or wait that reaches a node that does not store the partition, for example because the route was unknown and the request went to the client's own node, is refused with `NotPrimary`, and the request looks the route up again and resends once, so no refusal reaches the application. A filtered read or acknowledgment whose primary does not answer, the resend included, looks the route up again every second and follows the partition to the node the cluster names, instead of waiting out the client's 30-second call deadline on a stopped primary. It follows such a move once per request. A partition that moves again while the followed request waits is reported as unavailable, and the reader's next round looks the route up afresh.

## Consumers and polling

- A live consumer reads with polls the server holds. `max_wait` (Rust `ConsumerBuilder::max_wait(Duration)`, Python `max_wait_ms`, TypeScript `maxWaitMs`) is how long the server holds a poll that finds fewer than `min_count` new records, 5 seconds by default and at most 600 seconds. Zero answers at once. A record that lands ends the wait at once, so the default adds no latency. `min_count` (default 1, at most the batch length) ends a held poll early, and `max_bytes` (default 1 MiB, at least the server's minimum) caps the record bytes of one reply. A record larger than `max_bytes` comes alone, so a read always makes progress. A policy-aware group consumer passes `max_bytes` to the group reader as its page byte cap, clamped to the 8 MiB filtered page cap (`MAX_FILTERED_PAGE_BYTES`). There too a first record larger than the cap comes alone, and only a record larger than 8 MiB stops its partition with `FilterOversizedRecord`. `poll_interval` and `auto_join_group` are gone: a group consumer always joins its group.
- One-shot reads, such as replays, cursors, context reads and snapshots, never wait. A loop that reads a partition to its end reads until an empty reply or past the partition's current offset, because a reply that reaches `max_bytes` can hold fewer records than it asked for without being the end.
- On the native consumer the commit policies map onto Apache Iggy's: `Disabled` commits nothing, `Polling` and `IntervalOrPolling` let the server store the offset of each read, `Interval(d)` stores every `d`, `All` and `IntervalOrAll(d)` store at the end of each batch, `Each` and `IntervalOrEach(d)` after each record, and `Every(n)` and `IntervalOrEvery(d, n)` every `n` records. A client-side store counts a record once the application asks for the next one, and the interval applies when one is given. Python uses the same consumer, and TypeScript applies the same rules in its own poll loop.
- The default commit policy is `All` (Python `auto_commit="all"`, TypeScript `{ kind: "all" }`) in all three clients: one store once the last record of a poll is handled and the handled prefix at shutdown, so a crash delivers the rest of the poll again on Apache Iggy and on a managed group alike. An unnamed TypeScript consumer stays `disabled`. `Polling` stores each batch on the server as it is read, before the application has handled it.
- A native commit (`commit(message)`) stores the record's offset under the partition history and reader that delivered it. A record read before its topic was recreated, its partition moved to another member, or a seek of its partition stores nothing, an automatic store refused for the same reasons is dropped and the record is read again by its current reader, and a record this consumer did not deliver is refused as invalid. Under `Polling` and `IntervalOrPolling` the server already stored the record's batch on read. `store_offset` (TypeScript `storeOffset`) stays the explicit, unfenced store.
- `seek(partition, start)` on a native consumer (Python `seek(partition, polling=, offset=, timestamp_micros=)`, TypeScript `seek(partitionId, start)`) reads the partition next from the start it names. The rest of the partition's polled batch and the record in hand are dropped and count no more, so the sought records are delivered again. Under the polling policies a seek to an offset above zero first stores the offset before it, every other seek stores nothing. A policy-aware group consumer refuses it as invalid, like `store_offset`, because a position outside a delivery bypasses the group's acknowledgments.
- Replay reads (`Topic::replay`, typed `records`) keep every user header with its wire type, like a live consumer: Rust `Message.headers` and `TypedRecord.headers` are `Headers`, Python's are typed values with `header_kinds`, TypeScript's a `ReadonlyMap` of `HeaderValue`.
- The native consumer recovers a partition its reader stopped. A fetch whose outcome is unknown, or a partition lane that such a fetch blocked, abandons that operation and resumes the partition after its stored offset. A partition whose history changed resumes after its stored offset. A partition the reader stopped after lasting refusals (a missing permission, a partition the group does not own, a missing stream, topic or partition) reports the refusal and resumes after its stored offset once the cause clears. Rust and Python report it each time the reader stops the partition, after six refusals in a row, and TypeScript, which has no upstream reader, reports the sixth refused poll in a row on a partition and counts again from there, so all three report a lasting refusal at the same pace. A partition consumer that commits on read and loses a permission does not reach that stop: the upstream reader treats a refused committing fetch as an outcome it cannot prove, reads the partition again every retry interval and recovers by itself when the permission returns, without a report (an Apache Iggy limitation, the stop is reached under `Disabled`, `Each`, `All`, `Every` and `Interval`). A record that does not decode is reported once as an error and skipped. Any other read error is reported while the reader retries by itself. Without `allow_replay`, a commit or an explicit offset store at or below the offset the consumer stored last is not sent, so the stored offset never moves back.
- The agent runtime reads with held polls too. Rust `Agent::builder().max_wait(..)`, Python `spawn_agent(max_wait_ms=)` and TypeScript `maxWaitMs` set the wait, 5 seconds by default. The shared reply reader and the agent control follower hold their reads instead of sleeping between passes, one held fetch per primary. When one primary refuses its fetch, the other held fetches end at once and every partition is read again, so a reply on that primary's partitions does not wait out the hold. The reply reader holds them only while a request waits for a reply: when the last waiter leaves it drops its reads at once, which cancels them on the server, so an idle client holds nothing. The control follower holds its reads while its agent runs and drops them when the agent stops.
- A group consumer, native or policy-aware, always reads after the group's stored offset. Its start (Rust `start_at`, Python `polling`, `offset` or `timestamp_micros`, TypeScript `startAt`) only applies to a partition the group never stored: before the first read of such a partition the consumer stores the offset before the record its start names. `Offset(n)` stores n - 1, a timestamp the record before the first one at or after it, or the last record when every record is older, `Last` the record before the last one, so the last record is delivered first, and `First`, `Next`, offset 0 or an empty partition store nothing. It stores those of the partitions it holds when it joins at once, and one it gains later, such as one another member held without storing or one created after the join, before its first read when the group still stored nothing there. A partition the server has not installed for the member yet refuses the store and keeps its seed, unread, until a later sync shows it held. A failed lookup or a refused seed, such as an offset past the end (`InvalidOffset`), fails the start (Rust `build`, Python `init` or the first `next`), or that first read, with the Iggy error, and a failed start leaves the group. The one exception is the Rust and Python native group consumer, which only a server without group policy reads uses (the fork makes every group consumer policy-aware): it seeds only the partitions it holds when it joins, after waiting up to 10 seconds for the server to install them, because the upstream reader reads a partition it gains at once and offers no hook to seed it first, so a partition it gains later with nothing stored begins at its first record. A native group reader starts at `Next` on every partition, so a rebalance never restarts a partition at the configured start. Partition consumers and a `FilteredReader` built with `start` keep their start.
- A group reader whose whole round found nothing new waits on the server with a filtered wait when `Capabilities.filters.max_wait` (Python `max_wait_ms`, TypeScript `maxWaitMs`) is non-zero. It waits the smaller of its own `max_wait` (Rust `FilteredReaderBuilder::max_wait(Duration)`, Python `reader(max_wait_ms=)`, TypeScript `maxWait(ms)`, 5 seconds by default) and the announced limit, then polls the partitions the server reports ready. A server that announces zero gets no wait, a wait refused as unsupported stops waits for that reader, and a wait refused by a node that no longer serves its partitions, or refused as `unavailable` by a backup, is sent again at once to the routes looked up again, so only a second refusal in a row, any other failure, or an empty answer well before the wait elapsed falls back to one `idle_interval` sleep. While its waits are held, a group reader reads its assignment again every 2 seconds, and a changed assignment ends the wait, so a partition gained in a rebalance is read within about 2 seconds and not when the wait elapses. Each wait carries an id unique within the process. When one node answers ready, when the assignment changes, and when the reader closes or is dropped, the reader cancels the waits still held on the other nodes (`AGDX_FILTERED_WAIT_CANCEL`), so they free their server slots at once. A failed cancel is ignored, the server ends the wait at its deadline. A ready answer that a page confirmed lets the next idle round wait again. A normal group consumer on a server that resolves group policies uses the same reader with the consumer's `max_wait`, and with an interval commit policy and handled records not yet stored it waits at most until that store is due. A Rust caller that drives its own loop with `try_next_page` or `read_round` calls `FilteredReader::wait_for_records` after a round that found nothing new. A page call with a timeout (TypeScript `nextPage({ timeoutMs })`) bounds its wait by what is left of the timeout and cancels the held waits when it runs out. The Rust reader takes `&mut self` and Python serializes its calls, and the TypeScript reader runs one call at a time, so overlapping calls queue instead of reading the same records twice.
- A group reader classifies the capability probe like the group consumer: a probe that established nothing fails with the retryable timeout, a server that positively lacks consumer filters refuses with an unsupported error on surface `filters` and no feature, and a server that serves filters without group reads asks for an upgrade with feature `group_policy_reads`. Every delivered record says how the policy treated it: `selected`, `unevaluated` with the fault reason (a pass fault, foreign or mismatch policy delivered it without evaluation, for example `malformed`, `foreign_codec` or `type_mismatch`) or `unfiltered` (the group has no policy). Rust carries the reason in `RecordEvaluation::Unevaluated(FaultReason)`, TypeScript in `{ kind: "unevaluated", reason }`, and Python in `MatchedRecord.unevaluated_reason` beside the `evaluation` word.
- A record the filter cannot evaluate under the `stop` fault policy, the default, or a record larger than the 8 MiB filtered page cap stops its partition. The read fails with Rust `LaserError::FilterFault` or `FilterOversizedRecord`, Python and TypeScript `FilterFaultError` or `FilterOversizedRecordError`, naming the partition and the record's offset. The record and everything after it stay unacknowledged, the other partitions keep reading, and the stopped partition is read again each idle interval until the record ages out or the caller skips it. `skip(partition, offset)` on the group reader and on the policy-aware group consumer (Python `skip(partition_id, offset)`, TypeScript `skip(partitionId, offset)` with a `bigint` offset) passes exactly that record, as a native consumer seeks past it: the reader stores `offset` with a fenced acknowledgment under the policy and the owner the stopped page was read under, once every earlier record of the partition is handled, and the next read starts after it. A skip at another offset, or after the block is gone, fails with an invalid error, and a policy changed since refuses the acknowledgment with `conflict` and restarts the partition from its stored offset. A native consumer runs no filter and refuses `skip` with an invalid error. Its `store_offset` moves it.
- A change-feed reader (Rust `Watch::records`, Python `await laser.watch()`, TypeScript `watch().records()`) reads the capabilities again when it opens. It starts at the first retained change, at each partition's current end with `from_end` (TypeScript `fromEnd`), or at saved offsets. `poll` never waits, `poll_within` (TypeScript `pollWithin`) reads again every 100 ms until a change lands or the timeout passes. Each change carries its message id and feed position, the reader counts records retention removed before it reached them (`missed`) and records that are not change records (`skipped`), and a record of another version stops its partition and fails a read that has nothing else to deliver with the `VersionSkew` code. The [AGDX change feed](agdx.md#a118-the-change-feed) defines the record.

## Key-value expiry and session links

A value TTL is relative in all three clients: `ttl(..)` on a write and `expire(key, ttl)` send `ttl_micros`, and the managed backend adds it to the mutation's server timestamp when it folds the record, so no client clock can skew it and every replica stores the same expiry. `expires_at` and `expire_at` send an absolute epoch time instead. The later of the two calls on one builder wins, and a request carrying both is refused as invalid. A store linked to a session with `in_session(..)` (TypeScript `inSession`) links its fenced compare-and-swap writes too, like its sets, compare-and-swaps, deletes and patches.

## Coordination and ownership

All three clients expose the two-phase fenced-lease client. Prepare an acquisition, renewal, release, or fenced compare-and-swap once. The prepared object keeps its operation ID and exact frame bytes. Repeat it only when its recovery action allows that.

Each attempt has a 15-second timeout by default, above the managed backend's 10-second fold wait, so a mutation the fold has not applied yet comes back as a pending reply rather than a timeout. Rust takes a `Duration`, Python `timeout_ms` milliseconds, and TypeScript milliseconds. A timed-out attempt or a transport failure mid-request retires the connection, because a late reply on it would answer the next request, and reports a recovery action for that operation. After an uncertain acquisition, repeat the prepared object, or wait out the requested lease lifetime before acquiring under a new identity. Renew and release can repeat the prepared object. A fenced write needs reconciliation against its target.

The low-level client makes one attempt per call, reports the recovery action and leaves the recovery to the caller. Each `Laser` keeps one dedicated coordination connection, opened on first use. It carries every ordinary `Kv` acquisition (`lease`, `try_lease` and `lease_guard`, in TypeScript `lease`, `tryLease` and `leaseGuard`) and the lease renewals of an exclusive workflow step. Renewing or releasing through `Kv` (`renew_lease`, `release`, and a guard's `renew` and `release`) runs on the handle's shared connection, so a coordination reset never reaches it. A coordination call whose send fails or times out retires the connection, and that fails every other call in flight or waiting on it too. Each call retires only the connection it used, so a late failure from a connection that was already replaced leaves the replacement running. Each failed call is classified by whether its request bytes were written. A call whose frame was never written cannot have applied, so its error is returned as a definite failure: the client refused it before any link carried it, the connection shut down while it waited, or the connection was replaced after the call readied it. A call whose frame was written and whose reply was cut off fails with the ambiguous mutation error naming its own operation identity, and so does a call whose frame one node took while a later node in the same walk found the connection shut down. A timeout counts as written, because the frame may be on the wire. When the transport cannot tell, a retryable transport failure counts as written and any other failure as not. The next call opens a new connection and checks the fenced-lease capability again.

The ordinary calls recover from the ambiguous mutation error themselves, whether their own attempt failed or another call's reset cut it off. An acquisition repeats its prepared request, with the same operation identity and the same bytes, so the store answers with the outcome it recorded. It pauses 100 milliseconds before the first repeat and doubles the pause up to 2 seconds, never pausing past what is left of the window. The window is the requested lease lifetime measured from the first send. A failure after the window has passed is returned as the ambiguous mutation error, and a grant that arrives after its local deadline fails with the lease-lost error. An exclusive workflow step repeats an ambiguous renewal the same way, under the renewal's prepared identity and with the same pauses, until the earlier of the lease's local deadline and the step deadline. Each renewal attempt is bounded by the attempt timeout or the time left, whichever is shorter, and when the time is gone the renewal fails with the lease-lost error. Any error other than the ambiguous mutation error ends a repeat at once. An aborted TypeScript signal ends an acquisition's repeat at once, and the lease may then be held until its lifetime runs out. A dropped Rust future or a cancelled Python task leaves the acquisition's repeat running in its own task until it resolves. Acquisitions of different keys never wait behind each other. Reads return plain timeouts. Readiness and request validation fail before anything is sent.

A reply that names no outcome yet is ambiguous like a lost one: `Pending` (the backend accepted the frame and has not folded it), `BackendUnavailable` (the node could not reach its backend) and `Unavailable` (the node shed the request) each fail with the ambiguous mutation error naming the prepared operation identity, so the prepared bytes and identity stay available for the operation's own recovery: an acquisition repeats the prepared frame within its requested lifetime, a renewal or release repeats the prepared frame, and a fenced compare-and-swap reconciles through its target precondition. Such a reply arrived whole, so it leaves the connection open for the other requests on it. The managed backend answers a repeated identity with its recorded outcome. Rust, Python and TypeScript behave the same way.

A granted lease carries its local deadline: Rust `Lease::valid_until` (an `Instant`), Python `Lease.valid_until` (seconds on the `time.monotonic()` clock) and TypeScript `Lease.validUntilMs` (milliseconds on the `performance.now()` clock). It is the first send of the grant or renewal plus the granted lifetime. The store starts the lifetime no earlier than it received the request, so work that stops before the deadline never outlives the lease, however late the reply arrived. An ordinary `Kv` acquisition whose grant arrives after its deadline fails with the lease-lost error instead of returning a lease that is already dead, and an exclusive workflow step renews before its lease's deadline and stops at it. A grant or workflow renewal answered over the dedicated coordination connection raises the read-your-writes frontier of the handle that asked, so its next read observes the acquisition. A dedicated connection to a deployment without fenced leases probes the capability again at most once a second.

`close` is terminal. `reset` retires the transport connection and allows reuse. A transport that replaces its connection reports its `generation` and implements `send_on` and `reset_generation` (TypeScript `sendOn` and `resetGeneration`), so the client sends on and retires only the connection a call readied. The defaults send on and reset the current connection. A dedicated transport's readiness check waits until the old connection is retired. A closed `Laser` cannot reopen its coordination connection.

An agent handle owns its worker. Python follows the same rule as Rust, and TypeScript handles support asynchronous disposal. The shutdown grace period bounds pending SDK work, and application callbacks must honor cancellation.

Periodic consolidation needs both an interval and a consolidator. The consolidator owns its memory and receives the agent's own scope. A failed pass does not stop later ticks. `join` keeps consolidation running until the worker exits.

## Memory and context

`ConsolidationReport` counts summarized, reweighted, pruned, and derived items. The default pass looks at no more than 10,000 items, keeps the newest IDs, and counts only removals that succeeded. The built-in summarize pass writes one durable `Summary` item per conversation whose turns have no summary yet, `summarized` counts only the turns it summarized in that pass, and optional pruning removes the messages it covered. Log storage does not persist a separate lifetime field.

`MemoryHandler` remembers a successfully handled message under its conversation, attributed to the agent handling it, never to the sender. A context without an agent id stores the item with no agent. It stores nothing until `auto_remember` selects a kind. A failed memory write does not run the handler again and is reported as a warning: a `tracing` event in Rust, a `laser_sdk` log record in Python, and a `LaserWarning` process warning in TypeScript.

Lifetime is metadata for writes and custom backends. Built-in recall filters on identity fields, not on lifetime. A reranked handle keeps explicit kinds and content IDs. A custom backend keeps the custom callback contract and does not gain named-item operations from the code behind it.

Context assembly supports custom policies, ancestry, start offsets, and checkpoints. Each partition read examines at most 10,000 raw records before it filters by conversation. A checkpoint takes precedence over raw start offsets. A captured checkpoint names its stream and the creation time of each topic it covers, and a read with it on another stream or on a recreated topic fails with an invalid error. TypeScript `LastN` and `TokenBudget` refuse a bound that is not a non-negative safe integer. A custom selection keeps the source topic of each message.

Python takes full memory scopes and queries as keywords. `to_context_block` renders recall results in the order given and keeps the first item even when it alone exceeds the token estimate.

## Durations, deadlines, and cancellation

A relative duration is a `std::time::Duration` in Rust, a millisecond number named with `Ms` in TypeScript (`timeoutMs`, `ttlMs`, `everyMs`), and a millisecond float named with `_ms` in Python (`timeout_ms`, `max_wait_ms`, `deadline_ms`), which takes an `int` or a `float`. A negative, NaN, or infinite value fails with an invalid-argument error before anything is sent. Fractions of a millisecond are kept to the microsecond where the wire counts microseconds. An absolute instant is epoch microseconds named with `at` (`deadline_at_micros`, TypeScript `deadlineAtMicros`, Rust `Provenance::deadline_at` as an `IggyTimestamp`), and a relative budget never is (Rust `deadline(Duration)`, Python `deadline_ms`, TypeScript `deadlineMs`). Timestamps read from the log (`timestamp_micros`, `observed_at_micros`) stay raw epoch microseconds. Wire types keep their wire field names, such as `Query.deadline_micros` and `Window.every_micros`.

Every TypeScript call that returns a promise takes a trailing options object with an optional `signal` (`CallOptions`), merged into the call's own options object when it has one: `kv.get(key, { signal })`, `consumer.nextWithin(1_000, { signal })`, `reader.nextPage({ timeoutMs: 500, signal })`. A signal is never a positional argument. An aborted signal rejects the call with `CancelledError` before it sends anything and, once it aborts, while it waits. A held wait (a consumer poll, a filtered wait, a reply wait) is cancelled on the server, and a polling or retry loop of the SDK (readiness, materialization, lease and filter outcome waits, producer backoff and linger) stops. A plain request is abandoned: the call rejects at once and its reply is dropped. A publish (`Topic.send` and `batch`, the publish builders, `Producer`, `BatchingProducer`, the AGDX verbs and chunk streams, `sendAgent`, session, memory and registry records, a dead-letter redrive) starts no new attempt and no retry wait once its signal aborts, and a retry wait in progress ends at once ([publish recovery](publish-recovery.md)), as with a dropped Rust future or a cancelled Python task. The one exception is `Sessions.submit`: once its submitted status write starts, the status and the command run to completion, so a session never stays submitted without its work. Teardown (`close`, `shutdown`, a lease guard's `release`) and the interfaces an application implements take no signal, except that a `Memory` backend's writes receive the caller's options.

Rust cancels by dropping the future, and Python by cancelling the task (`task.cancel()`, `asyncio.timeout`, `asyncio.wait_for`), which drops the Rust future under it. Both end held waits the same way: a dropped reply wait leaves the reply reader, and a dropped or closed filtered reader cancels the waits it holds. In all three clients an abort after a write was sent does not undo it, so the outcome of an aborted publish or mutation is unknown, as with a lost reply, and a retry should reuse the same idempotency or mutation identity.

## Portable helpers and callbacks

The pure A2A and MCP converters keep the original request bytes and open no connection. Card signatures, delegation checks, claim checks, snapshot bytes, resume offsets, and reciprocal-rank fusion follow the same native contract in every client. Python exports them in snake_case, for example `encode_snapshot` and `decode_snapshot`, and TypeScript in camelCase, for example `encodeSnapshot` and `decodeSnapshot`. `SystemClock` and `TestClock` count epoch microseconds as unsigned 64-bit values.

Python workflow builders, verifiers, and compensation callbacks can return a value directly or through an awaitable. Objects with `build` or `verify` methods work too. A custom snapshot store implements `latest(conversation)` and `save(snapshot)`, and `state_with` accepts it directly or wrapped in `SnapshotStore`. Callback errors keep their SDK class, and cancellation retires the asynchronous work in flight.

A custom Python route policy is `None`, a built-in policy name, or a synchronous callable or object with a `select` method. The scorer receives `skill_id` and `RouteCandidate` objects with `agent`, `card`, and `capability`. It returns a candidate index, or `None` to refuse them all. An async scorer is rejected.

## Retry and deadline table

Every client reads its retries and deadlines from one table: `sdk/src/retry.rs` in Rust, which Python uses, and `src/retry.ts` in TypeScript. Both are tested against `sdk/tests/fixtures/retry-table.json`. A backoff doubles per consecutive failure from its base up to its maximum, and each wait is drawn at random from the upper half of that delay.

| Surface | Values |
| --- | --- |
| Managed mutation and control append | backoff from 100 ms to 2 s, 30 s deadline, each attempt bounded from 1 s doubling within it |
| Presence advertise and clear | one attempt of 5 s on the replica that holds the presence |
| Reliable consumer and pause runtime reopen | backoff from 50 ms to 1 s, gives up after 10 consecutive failures |
| Control topic discovery | waits up to 30 s between looks |
| Consumer-group filter change | 3 attempts 200 ms apart, outcome awaited 30 s |

| Producers racing to create a stream or topic | 10 attempts |

## Managed mutation outcomes

A managed mutation keeps one operation identity for every attempt. When the server reports `Pending`, reports `BackendUnavailable` because the managed backend behind the node did not answer, reports `Unavailable` because the node shed the request, or the connection fails after the request was sent, the client sends the same request again with jittered backoff. The server applies a mutation at most once for one identity and returns the recorded outcome to a repeat. If the outcome is still unknown after 30 seconds, the call fails with `AmbiguousMutation` (`AmbiguousMutationError` in Python and TypeScript). The error carries the operation identity as Rust `operation_id: Option<u128>`, Python `operation_id` and TypeScript `operationId`, absent only when the mutation was never sent under one, and a repeat under that identity returns the recorded outcome. The mutation may still apply, so check the target state before you issue new work. A filter catalog outcome read by `operation` or `mutate` whose version, operation identity or catalog position identity differs from the request is refused as a protocol error. Rust, Python and TypeScript behave the same way. Python uses the Rust client.

A mixed-operation batch (`execute_batch`, TypeScript `executeBatch`) runs its items one after another in input order, so a set followed by a get of the same key reads the new value. It is one such frame: its parent identity and its input order give every item a derived identity of its own. An item whose slot reports `Pending`, `BackendUnavailable` or `Unavailable` leaves the frame unresolved, and the client repeats the whole frame under the same parent identity until every slot is final or the 30 second deadline passes, so a mutation item applies once and returns its recorded outcome on a repeat while a read item runs again. An item that was unresolved and is then refused by admission (`Forbidden`, `Unauthenticated`, `StepUpRequired`) ends the call with the ambiguous mutation error naming the parent identity and the item. The backend reserves reply room for every item before it dispatches any: a mutation that cannot reserve room for its outcome is refused in its own slot before it has any effect, a read whose result does not fit the remaining room is refused in its own slot with `TooLarge` after the mutation outcomes are placed, and a completed outcome is never replaced by a frame-level failure.

The three authorization writes keep a receipt of their outcome under the account that sent them. `define_role_as`, `delete_role_as` and `bind_roles_as` in Rust (TypeScript `defineRoleAs`, `deleteRoleAs`, `bindRolesAs`, Python the `mutation_id=` keyword on `define_role`, `delete_role` and `bind_roles`) take the receipt identity from the caller, validated by the shared mutation id rule before the send. A repeat with the same identity and content after a lost reply returns the original outcome without a second effect, also for an administrator that revoked its own administration, so a binding revision moves once. The same identity with other content is refused as a conflict, and a new identity that finds no receipt room inside the server's replay floor is refused as a resource limit. The plain verbs mint a fresh identity per call.

When the node a client is connected to answers `BackendUnavailable`, or its managed connection fails, a client built from a connection string moves its managed requests to another node of the cluster. It reads the roster, skips the failed node and nodes that report themselves stopping or unreachable, and dials the next node directly instead of following the leader redirect. Before it uses that node, it checks that the node's managed backend is ready and announces the same operation versions the client negotiated. A mutation keeps its operation identity and its deadline across the move. A read moves once when its node answers `BackendUnavailable`. Later requests stay on the new node. When the new node's connection fails during a read, the error goes to the caller and the next request uses the original connection again. After a move, the first key-value, fork, graph and session read each carries a read barrier. The new node answers it only after its fold has applied every mutation its log held when the read arrived, or for a session read every record its session source partitions held, so the read sees the client's own earlier writes. A node that does not get there within its wait bound answers `Stale`, and the next read carries the barrier again. A client built from an existing Iggy client cannot dial another node, so it keeps repeating on its own connection. Rust and TypeScript behave the same way. Python uses the Rust client.

Every managed key-value, fork and graph reply carries the position each of the answering node's folds had applied. The client keeps the highest position it has seen per surface and sends it with every later read of that surface. The node that answers serves the read only once its fold has applied that position, and answers `Stale` when it does not get there within its wait bound. So a read never misses the client's own earlier writes and never goes back behind an earlier read, whichever node answers. After a mutation topic is recreated, the first read that still names the old topic answers `Stale` and brings the new topic's position back, so the next read goes through. A session watch waits through `Stale` as it waits for a new change, so a watch that moved to a node that has not folded its stream yet keeps going instead of failing. Session reads work the same way per stream and source partition. A session read reply carries the session fold's position on every source partition of its stream, and the next session read sends the positions the client has seen. A position on a stream or topic that was deleted or recreated since, or on a topic the stream no longer registers, is ignored by the node, so it never holds a read back. Clones of one client share its positions. `seen_positions()` in Rust and Python and `seenPositions()` in TypeScript return them.

Live client presence is stored on the node that receives it. `client_metadata().all()` in Rust, `client_metadata_all()` in Python, and `clientMetadata().all()` in TypeScript, collect matching connections from every node. Each node has its own page cursor. A single-page request reads the caller's node.

A presence is pinned to the replica that received it. The first `advertise_presence` (TypeScript `advertisePresence`) pins the replica that answered, and every later advertise or `clear_presence` (`clearPresence`) of that connection goes to the same replica, so a client whose managed requests moved to another node never leaves a stale presence behind and never advertises a second one elsewhere. Advertise and clear are serialized. While the pinned replica does not answer within 5 seconds the call fails as unavailable and keeps the pin, so a clear is never reported for a presence that is still advertised. A clear that reached the replica releases the pin and the connection's agent identity. Rust, Python and TypeScript behave the same way.

## Writer schemas

`CompiledSchema` compiles a registered writer schema and decodes a body into the model every client, consumer filters, the managed projector and the registry's decode share ([AGDX spec](agdx.md#a14-consumer-filters)): schema field names, numeric Protobuf enums, exact 64-bit integers, bytes and fixed values as arrays of byte values, proto3 scalars without presence at their default, repeated and map fields always present, unset fields with presence absent, Avro unions as their branch value, and Avro logical types as their physical values (a decimal is its unscaled bytes, a timestamp its long). `encode_avro` (TypeScript `encodeAvro`) takes the same physical values, and a union takes the first branch that accepts the value. Rust and Python decode exact integers. TypeScript decodes the 64-bit integer types (Avro `long`, Protobuf `int64`, `uint64`, `sint64`, `fixed64`, `sfixed64`) to `bigint` and narrower integers to `number`, and a JSON integer outside the safe range stays a `bigint`. The shared corpus `wire/fixtures/writer_schema_cases.json` pins the model in every client and on the server.

The registry accepts a definition of at most 1 MiB and JSON nesting 64, and a JSON Schema in draft 2020-12 only: a `$schema` naming another draft is refused before the request is sent. Ids start at 1 in every registry, and a registry holds at most 1,024 schemas, active and tombstoned together, so a registration past that is refused with the `resource_limit` result code while other streams keep their own budget. A registration that does not compile fails with `Invalid`, a decode under an unknown id with a not-found error, and a decode payload over 1 MiB with a too-large error. `Schemas::list()` pages by offset: `.page(n)` counts from 1 (0 reads the first page), `.results(n)` is 10 by default and at most 100, and `.fetch()` answers a `SchemaPage` with `items`, `page`, `total_pages` and `total_results` in id order. TypeScript spells it `list().page(n).results(n).fetch()`, and Python takes `list(name_contains=None, page=0, results=0)` and returns the page as a dict.

## Materialization and operational SQL

Materialization setup is available in Rust, Python, and TypeScript through `topic.materialize().apply()`. It registers a whole-record projection by default. A typed projection selects extracted fields. Reuse the setup operation identity after an uncertain response. The resulting handle reports binding status and waits against a captured source target. Readiness and complete historical coverage are separate results. A topic feeds one index, so applying a setup with another index to a topic that is already materialized moves it: the earlier index stops receiving rows and keeps the ones it has. `topic.materialization(projection_id)` returns the handle `apply` returned, read under the topic's own stream, for a process that did not run the setup. A setup without an explicit projection id or typed projection uses the index name, which defaults to the topic name. `laser.materialization(projection_id)` reads every binding of the projection under the handle's default stream.

A status read answers no status (`None` in Rust and Python, `undefined` in TypeScript) when no projection has the id, and, for a handle from `apply` or `topic.materialization`, when its source is no longer bound to its index. A binding whose index the caller may not read is left out, and a status read is refused as unauthorized when the caller may read none of the projection's binding indexes, so a wait ends with that error rather than its timeout. Each binding status names the class of the last failed table creation as `failure`: `configuration`, `schema`, `poison` and `fatal` last until the binding or its backend changes, `transient`, `capacity` and `read_only` do not. `stall` says why nothing visible moves although no record holds the binding: `source_missing`, `source_unreadable`, `destination_unreadable` or `backpressure`. A binding applied for an earlier incarnation of its source stream holds every partition with the cause `retired_incarnation`, and applying it again materializes the live stream.

`wait(level, timeout)` returns `not_found` when the status is gone, `blocked` when a record or a history gap holds a partition, `failed` when a permanent class failed table creation, `ready` once every binding reaches the level, and `timed_out` with the last status otherwise. A `caught_up` wait whose source topic is recreated measures the new incarnation, since the records the first capture named are gone. The wait pauses 50 ms after its first read and doubles the pause up to 1 s.

A held record stays held until the binding is applied again with the dead-letter invalid-record policy, which skips it to the dead-letter topic. A history gap stays until an operator accepts it. Clients cannot skip records or accept gaps themselves. Complete history needs every partition the binding passed to start at offset zero, and a partition whose records all expired before the binding read them reports a first offset past them, so it never counts as complete.

Projection history defaults to append. Keyed history selects a typed header key or a payload JSON pointer and can name a delete header. A key stays in one partition per topic incarnation. Older updates cannot replace a newer value or restore a deleted value. A record that carries the delete header removes its key. The delete header is optional: a keyed view without one never deletes, so a record carrying a header named `deleted` or `delete` replaces its key's row like any other update. Rust `keyed(key, None)`, TypeScript `keyed(key)` and Python `keyed(key)` build such a view, and Rust `keyed(key, Some("deleted"))`, TypeScript `keyed(key, "deleted")` and Python `keyed(key, delete_header="deleted")` name one. A typed keyed record with no extracted field is an invalid record under the binding's invalid-record policy and never removes its key. Keyed history does not claim complete append history. Projection and binding history cannot change in place: registering a projection again with another history or kind answers `Conflict`, and a binding that names a projection that does not exist answers `NotFound`.

Bindings use `invalid_records` and `oversize` policies. Both default to block. Dead-letter handling permits automatic skips of rejected records. Reference handling omits an oversized body while retaining its source location. A record that fails its declared writer schema follows the invalid-record policy. A typed row keeps an inline copy of a body only up to the body limit its backend announces (`max_payload_bytes`), and over it the row keeps its fields while the log keeps the body.

`projections().list()` returns one page of the matching projections in id order: `page(n)` picks the 1-based page and `results(n)` the projections per page, 10 by default and at most 100. The reply carries `items`, `page`, `total_pages` and `total_results`, and counts only the projections the caller may read.

Raw SQL requires an explicit dialect in every client. Rust uses `raw_sql(dialect, sql)` or `raw_sql_with(dialect, sql, params)`. Python uses `raw_sql(dialect, sql, params=None)`. TypeScript uses `rawSql(dialect, sql, params?)`. Every referenced index must be authorized for the caller and belong to the same stream and backend. Unsupported managed capabilities fail explicitly on original Apache Iggy. Standard streaming remains available.
